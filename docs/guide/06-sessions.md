# 6. Sessions

← [Interactive TUI](05-tui.md) · [Index](README.md) · Next: [Tools & safety](07-tools-and-safety.md)

A session is the durable record of a conversation: every message, tool call and
tool result. Sessions are plain JSON under `.zcode/sessions/`, so they can be read,
diffed, committed, and handed to a colleague.

Ids generated by `zcode` are UUIDv7 — time-ordered, so sorting by name sorts by
age. Ids you choose yourself (`fork --as`) can be any short, safe name.

## Create

```sh
$ zcode session create
01a03bd4-b98d-7fe1-8721-872199d7573a
```

Prints the id and writes an empty session. Every `zcode run` without `--session`
does this implicitly.

## Continue

With a prompt, it runs headless:

```sh
$ zcode session continue 01a03bd4-b98d-7fe1-8721-872199d7573a "now add tests"
```

Without one, it opens the TUI on that session:

```sh
$ zcode session continue 01a03bd4-b98d-7fe1-8721-872199d7573a
```

Equivalent to `zcode run --session <id> "..."`. The full prior transcript is
replayed to the model, so it remembers what it did.

## Fork

Branch a conversation to try a second approach without losing the first:

```sh
$ zcode session fork 01a03bd4-b98d-7fe1-8721-872199d7573a
01a03bd4-b9a9-72f3-b591-c48215dad9e5
```

The child starts with a copy of the parent's history and is thereafter
independent.

Give the branch a name you will recognise with `--as`:

```sh
$ zcode session fork 01a03bd4-b98d-7fe1-8721-872199d7573a --as review-experiment
review-experiment

$ zcode session continue review-experiment "try the other approach"
```

Names may contain letters, digits, `-`, `_` and `.`, up to 64 characters. Path
separators, `..` and leading dots are refused, so a session id can never point
outside `.zcode/sessions/`:

```sh
$ zcode session fork <id> --as ../escaped
zcode: invalid session id: ../escaped
```

## Export and import

```sh
$ zcode session export 01a03bd4-b98d-7fe1-8721-872199d7573a --to backup.json
backup.json

$ zcode session import backup.json
01a03bd4-b99f-7733-aa35-b240123ddb5c
```

Import always allocates a **new** id, so pulling in a colleague's session can
never overwrite one of yours.

## Auto-checkpointing

The session is written after every step — after each tool round and after the
final answer. If the process is killed, the machine loses power, or you hit
Ctrl-C, the transcript on disk is current to the last completed step. Resume
with `zcode run --session <id>`.

## The file format

Sessions written before `editing` existed record `"mode": "build"`. They still
load — `build` reads as `auto` — and the next checkpoint writes the current
spelling. (`session export` copies the file verbatim, so an old export keeps
the old spelling; that is what makes it a faithful copy.)

```json
{
  "version": 1,
  "id": "01a03bd4-8313-7b32-9809-7d9984359dda",
  "created_at": "2026-08-26T02:09:38Z",
  "model": "demo-model",
  "mode": "auto",
  "last_message_at": "2026-08-26T02:09:38Z",
  "step_count": 2,
  "messages": [
    {
      "role": "system",
      "content": "You are an autonomous coding agent. Make edits directly ..."
    },
    {
      "role": "user",
      "content": "add a farewell function to src/main.rs"
    },
    {
      "role": "assistant",
      "content": "I'll add the function.",
      "tool_calls": [
        { "id": "call_1", "name": "apply_patch", "arguments": "{\"patch\": \"--- a/src/main.rs\\n...\"}" }
      ]
    },
    {
      "role": "tool",
      "content": "",
      "tool_result": { "tool_call_id": "call_1", "content": "patched src/main.rs (1 hunk(s))" }
    },
    { "role": "assistant", "content": "Added `farewell` to src/main.rs." }
  ]
}
```

`version` lets future releases read today's files. Writes are atomic
(temp file + rename), so a crash mid-write leaves the previous good copy intact.

## Housekeeping

There is no `session list` subcommand yet; the directory is the list:

```sh
$ ls -t .zcode/sessions/
$ jq -r '"\(.id)  \(.created_at)  \(.step_count) steps"' .zcode/sessions/*.json
$ find .zcode/sessions -mtime +30 -delete        # prune old ones
```
